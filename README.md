# FmtLog

Журнал для микроконтроллеров: уровни, источники и приёмники вывода.

```cpp
log::info(F("pin {} = {}, temperature {} C"), pin, level, 54.25);
```

![Цветной вывод журнала](docs/log-output.svg)

<sub>Снимок собран из настоящего вывода библиотеки — `tools/make-screenshots.sh`</sub>

Форматирование даёт [FmtTiny](https://github.com/240974a/FmtTiny) — она
подключается автоматически. Нужно только форматирование `{}` без журнала? Возьмите её
отдельно.

---

## Зачем

**Вы решаете, куда уйдёт сообщение.** Сама библиотека никуда не пишет — вы
даёте ей приёмник. Их может быть несколько: пока отлаживаете — в порт, на
рабочем устройстве — по сети, а на карту памяти — чтобы разобраться после
сбоя.

**У каждого источника сообщений свой уровень**: например - сеть рассказывает подробно, а датчики сообщают только выход за критические пороги.  
Библиотека проверяет уровень
раньше, чем начинает собирать строку, поэтому лишний вызов почти ничего не
стоит.

**Ничего не пропадает молча.** логи `critical` и `system` пройдут при любом пороге.
Если строка не влезла в буфер, вы это увидите. Если telnet-клиент отстал и
кольцевой буфер его догнал — тоже.

**В журнале настоящее время.** Скажите библиотеке, который час — из NTP, из
RTC, откуда угодно, — и вместо счётчика с момента запуска появится дата.

**Поток видно с одного взгляда.** Уровень и источник раскрашены, так что
ошибка не потеряется среди отладочных строк.

**Журнал доходит туда, где его читают.** Serial, Telnet и веб-страница — смотреть
глазами; Loki — искать по меткам в Grafana; SNMP — позвать дежурного, когда
случилось то, что ждать до утра не может.

## Как пользоваться

```cpp
#include <FmtLog.h>
using namespace fmtlog;

void setup() {
    Serial.begin(115200);
    log::addSink(log::serialSink);
    log::setLevel(Level::info);

    log::info(F("started"));
    log::err(F("sensor is silent {} times in a row"), 3);
}
```

Образец держите во флеше — через `F(...)`, тогда он не займёт места в RAM.

Что написано в образце, библиотеке всё равно: она ищет в нём только `{}`.
**Пишите на любом языке**, например по-русски:

```cpp
log::info(F("бойлер {} °C, насос {}"), 54.25, F("включён"));
```

### Уровни и источники

```cpp
enum Source : uint8_t { app, net, sensor };
const char* const kNames[] = {"app", "net", "sensor"};

log::setSourceNames(kNames, 3);
log::setLevel(Level::info);        // всем
log::setLevel(net, Level::debug);  // сети — подробнее

log::debugFrom(net, F("sent {} bytes"), 128);
```

Уровней семь:

| | | |
|---|---|---|
| `trace` | `T` | самое подробное |
| `debug` | `D` | отладочное |
| `info` | `I` | обычный ход дела |
| `warn` | `W` | что-то пошло не так, но работа продолжается |
| `err` | `E` | ошибка |
| `critical` | `C` | после этого работа продолжаться не может |
| `system` | `S` | пуск, остановка и прочие вехи |

Два последних уровня порог **не глушит** — они выводятся в журнал всегда.

А `FMTLOG_COMPILE_LEVEL` убирает вызовы совсем: соберите с
`-D FMTLOG_COMPILE_LEVEL=2`, и от `trace` с `debug` в прошивке не останется ни
кода, ни образцов.

Уровни можно хранить и у себя — скажем, в EEPROM, чтобы менять их снаружи, через интерфейс управления:

```cpp
log::setLevelSource([](uint8_t src) { return storedLevels[src]; });
```

Тогда библиотека спрашивает у вас уровень перед выводом каждой строки, и управление уровнями работает "на лету".

### Время

Пока время неизвестно, в первом столбце тикает счётчик с момента запуска. Сообщите
время — и там появится дата:

```
steady : 00000012.340 I app: before time is set
26-09-03 12:30:45.123 I app: time is known now
```

```cpp
log::setTime(epochSeconds);        // секунды эпохи Unix
log::setTime(epochSeconds, 250);   // и доля секунды, если известна
```

Часовой пояс библиотека не прибавляет: нужно местное время — передайте
местное.

Между вызовами она досчитывает время по `millis()`, а кварц уходит на секунды
в сутки. **Повторяйте вызов** — раз в час или чаще; каждый следующий сбрасывает
накопленную погрешность, а не добавляется к ней.

Отметка всегда занимает 21 знак, так что столбцы не поедут в тот момент, когда
время появится.

## Приёмники

Приёмник — обычная функция. Библиотека передаёт ей готовую строку, а дальше
решаете вы:

```cpp
void toNetwork(const Record& record) {
    if(record.level < Level::warn)
        return;                       // по сети шлём только важное
    udp.beginPacket(host, port);
    udp.write(reinterpret_cast<const uint8_t*>(record.text), record.length);
    udp.endPacket();
}

log::addSink(log::serialSink);   // в порт — всё
log::addSink(toNetwork);         // по сети — только предупреждения и ошибки
```

В `Record` приходит всё, что нужно для решения:

| поле | |
|---|---|
| `level` | уровень; `log::levelName()` даёт имя словом, `levelMark()` — букву |
| `source` | номер источника; `log::sourceName()` даёт имя |
| `epochSeconds`, `epochMillis` | календарное время; ноль, пока не задано |
| `uptimeMs` | время с запуска |
| `text`, `length` | само сообщение |
| `truncated` | не поместилось в буфер целиком |

Через приёмник можно делать и то, что журналом обычно не зовут: считать ошибки для
показа на экране, мигать светодиодом при сбое, копить последние строки в
кольцевой буфер. `removeSink` снимает один приёмник, `clearSinks` — все.

### Готовые приёмники

| модуль | что делает |
|---|---|
| `log::serialSink` | вывод в `Serial`, входит в `FmtLog.h` |
| [`FmtColor.h`](#цвет) | то же, но с раскраской уровня и источника |
| [`FmtTelnet.h`](#журнал-по-telnet) | через Telnet, с историей и цветом |
| [`FmtWeb.h`](#журнал-на-веб-странице) | на веб-страницу: цвет, поиск, выгрузка |
| [`FmtSnmp.h`](#уведомления-по-snmp) | trap на монитор — только `err` и выше |
| [`FmtLoki.h`](#строки-для-loki) | в Loki, рядом с Prometheus |

Своего в списке нет — напишите: приёмник это одна функция, а в `Record` есть
всё, что ему нужно.

## Цвет

Раскраска — отдельный модуль: если приложение его не использует, код не попадёт в прошивку.

Тем же цветом идёт и [журнал по Telnet](#журнал-по-telnet) — терминал понимает
те же последовательности ANSI.

```cpp
#include <FmtLog.h>
#include <FmtColor.h>

const char* const kNames[]  = {"app", "net", "sensor"};
const uint8_t     kColors[] = {color::white, color::cyan, color::green};

log::setSourceNames(kNames, 3);
color::setSourceColors(kColors, 3);

log::addSink(color::serialSink);   // вместо log::serialSink
```

Время всегда тусклое — оно нужно для отсчёта, а не для чтения. Уровень задаёт
цвет строки, источник печатается своим. Обрезанное сообщение помечается
красным многоточием.

Цвета уровней заменяются массивом на семь значений — `color::setLevelColors`.

Монитор порта в Arduino IDE управляющих последовательностей не понимает и
показывает их как мусор: там нужен обычный `log::serialSink` либо снятая
раскраска `color::setEnabled(false)`.

Модуль стоит **436 байт** флеша и только когда подключён.

## Журнал по Telnet

```cpp
#include <FmtLog.h>
#include <FmtTelnet.h>

void setup() {
    WiFi.begin(ssid, password);
    telnet::begin();
    log::addSink(telnet::sink);
}

void loop() {
    telnet::handle();   // звать в каждом проходе цикла
}
```

Подключившийся видит не только новые сообщения, но и накопленную историю.

**Строка та же, что в порту** — время, уровень, источник и текст, — и с цветом:
терминал понимает те же последовательности ANSI. Ничего включать не нужно,
цвет идёт сразу.

Убрать его, если журнал разбирают скриптом или терминал цвета не понимает:

```cpp
#include <FmtColor.h>

color::setEnabled(false);   // и в порту, и в telnet
```

Настройка общая для обоих приёмников: цвет либо есть, либо нет. Цвета уровней
и источников задаются там же — смотрите [Цвет](#цвет).

**У каждого соединения своё место в истории.** Чтение ничего не стирает, поэтому
второй и третий клиент получают ту же глубину, что и первый. Если медленный
клиент отстал настолько, что кольцевой буфер его догнал, он продолжает с самого
старого и получает отметку `[N bytes lost]` — потеря видна, а не случается
молча.

```ini
build_flags =
    -D FMTLOG_HISTORY_SIZE=4096     ; по умолчанию 2048
    -D FMTLOG_TELNET_CLIENTS=2      ; по умолчанию 4
```

Историю можно и не отдавать: `telnet::setSendHistory(false)`.

Модуль работает на ESP8266 и ESP32 — на платах без сети он не собирается.

## Журнал на веб-странице

```cpp
#include <FmtLog.h>
#include <FmtWeb.h>

void setup() {
    WiFi.begin(ssid, password);
    web::begin();
    log::addSink(web::sink);
}

void loop() {
    web::handle();   // звать в каждом проходе цикла
}
```

Плата отдаёт только поток строк по адресу `/log`. Сама страница —
[`extras/log.html`](extras/log.html) — лежит у вас на диске: откройте её в
браузере и впишите адрес платы.

Адреса, к которым вы подключались, остаются в списке у поля — к соседней плате
переключаются выбором, а не набором заново. Ненужный убирает кнопка `×` рядом:
вместе с адресом забывается и сохранённый от него журнал.

Адрес можно передать и ссылкой — тогда закладка сразу открывает нужную плату:

```
log.html?host=192.168.1.50:7890
```

Указанный в ссылке адрес главнее списка.

Так страница не занимает флеш, и править её можно, не трогая прошивку.

Что на ней есть:

- **цвет** — как в терминале, уровень и источник различаются с одного взгляда;
- **поиск** по тексту и источнику;
- **выбор уровня** — показать только предупреждения и ошибки;
- **скольжение по времени** — `−` и `+` с выбором шага: минута, десять минут, час,
  полсуток, сутки; выбранный шаг запоминается;
- **чтение не сбивается**: стоит перемотать выше, и страница замирает на
  прочитанном месте, а новые строки ждут за кнопкой «Читать последнее» —
  на ней же видно, сколько их пришло;
- **пауза** — остановить поток, чтобы прочитать не спеша текущий вид, без перемоток;
- **журнал переживает перезагрузку** — до 2000 строк хранятся в браузере, так
  что F5 посреди разбора ничего не теряет;
- **светлая и тёмная тема** — переключаются кнопкой, выбор запоминается;
- **выгрузка** — сохранить видимое в файл.

Открывший страницу позже увидит и то, что накопилось до него: у каждой вкладки
своё место в истории, и чтение её не расходует.

### Посмотреть без платы

Страницу можно попробовать, ничего не прошивая:

```
python3 tools/fake-board.py
```

Скрипт притворяется платой: отдаёт историю за несколько дней, а дальше сыплет
строками по одной. Откройте `extras/log.html`, впишите напечатанный адрес — и
увидите то же, что увидели бы с настоящей платы.

### Почему SSE, а не WebSocket

Поток здесь односторонний: плата шлёт, браузер читает. Для такой задачи SSE
проще — это обычный HTTP-ответ, который не закрывают, и строка в нём выглядит
как `data: ...`. Не нужны ни рукопожатие с кадрированием, ни отдельная
библиотека, а при обрыве связи браузер переподключается сам.

```ini
build_flags =
    -D FMTLOG_WEB_HISTORY_SIZE=8192   ; по умолчанию 4096
    -D FMTLOG_WEB_CLIENTS=1           ; по умолчанию 2
```

Страница и плата — разные источники, поэтому в ответе стоит заголовок
`Access-Control-Allow-Origin: *`, иначе браузер заблокирует запрос. Плата
только отдаёт журнал и ничего не принимает, так что открывать его для чтения
безопасно.

Нужна своя страница? Формат строки простой:

```
data: 26-09-03 12:30:45.123⇥I⇥app⇥boiler 54.250 C
```

Время, буква уровня, источник и текст, разделённые табуляцией.

Модуль работает на ESP8266 и ESP32.

## Уведомления по SNMP

Не всё, что попадает в журнал, стоит внимания дежурного. `FmtSnmp.h` шлёт
монитору только то, что требует вмешательства, — `err` и выше:

```cpp
#include <FmtLog.h>
#include <FmtSnmp.h>

void setup() {
    WiFi.begin(ssid, password);
    snmp::begin(IPAddress(192, 168, 1, 10));   // где ждёт монитор
    log::addSink(snmp::sink);
}

void loop() {
    snmp::handle();   // звать в каждом проходе цикла
}
```

Уходит trap SNMPv2c на порт 162 — туда, где его ждёт Zabbix, PRTG, Nagios или
другой монитор. Порог меняется через `snmp::setLevel()`.

В trap идут три переменные: текст сообщения, номер уровня и имя источника. По
двум последним фильтруют на стороне монитора, не разбирая текст. Ветку OID
задайте свою — у организации она обычно есть:

```cpp
snmp::setEnterpriseOid("1.3.6.1.4.1.12345");
```

Пока её нет, берётся ветка для проб — `1.3.6.1.3.1`, её хватает, чтобы
настроить монитор.

Проверить без монитора можно так:

```
snmptrapd -f -Lo -c /dev/null 162
```

Отправка идёт из `handle()`, а не из `sink()`: тот вызывается изнутри
`log::err()`, и сети там не место. Пока монитор недоступен, события ждут в
очереди на четыре записи; переполнение видно в `snmp::lost()`.

Модуль работает на ESP8266 и ESP32.

## Строки для Loki

[Loki](https://grafana.com/oss/loki/) хранит логи так же, как Prometheus —
метрики, и смотрят их в той же Grafana.

```cpp
#include <FmtLog.h>
#include <FmtLoki.h>

void setup() {
    WiFi.begin(ssid, password);
    loki::begin("192.168.1.10");        // порт 3100 по умолчанию
    loki::addLabel("job", "boiler");
    loki::addLabel("instance", "kitchen");
    log::addSink(loki::sink);
}

void loop() {
    loki::handle();   // звать в каждом проходе цикла
}
```

Метки — то, по чему потом ищут. `level` и `source` библиотека ставит сама,
остальные задаёте вы:

```
{job="boiler"}                     всё с этой платы
{job="boiler", level="error"}      только ошибки
{job="boiler"} |= "pump"           строки со словом pump
```

Меток должно быть немного: в Loki каждое их сочетание заводит отдельный поток.

Строки уходят пачками — по шестнадцать или раз в пять секунд, что случится
раньше. Перед перезагрузкой или сном позовите `loki::flush()`, иначе последние
строки останутся в буфере.

Если приложение вызывало `log::setTime()`, строки лягут по настоящему времени.
Иначе время поставит сам Loki при получении — это лучше, чем считать от запуска
платы и промахнуться на десятилетия.

### Посмотреть без своего сервера

Loki и Grafana поднимаются одной командой — в
[`extras/loki`](extras/loki) лежит готовый контейнер:

```
cd extras/loki
docker compose up -d
```

Grafana откроется на <http://localhost:3000>, источник данных в ней уже
прописан, пароль не спрашивается. Подробности и разбор частых заминок — в
[extras/loki/README.md](extras/loki/README.md).

Модуль работает на ESP8266 и ESP32.

## Настройка сборки

| макрос | по умолчанию | что задаёт |
|---|---|---|
| `FMTLOG_MESSAGE_SIZE` | 128 (AVR: 64) | размер буфера сообщения |
| `FMTLOG_SOURCE_COUNT` | 8 | число источников |
| `FMTLOG_COMPILE_LEVEL` | 0 | порог отсечения при сборке |
| `FMTLOG_HISTORY_SIZE` | 2048 | история для telnet |
| `FMTLOG_TELNET_CLIENTS` | 4 | одновременных соединений |
| `FMTLOG_WEB_HISTORY_SIZE` | 4096 | история для веб-страницы |
| `FMTLOG_WEB_CLIENTS` | 2 | одновременных вкладок |
| `FMTLOG_SNMP_QUEUE` | 4 | событий в очереди SNMP |
| `FMTLOG_SNMP_TEXT_SIZE` | 96 | знаков сообщения в trap |
| `FMTLOG_LOKI_BATCH` | 16 | строк в пачке |
| `FMTLOG_LOKI_INTERVAL_MS` | 5000 | когда слать неполную пачку |
| `FMTLOG_LOKI_TEXT_SIZE` | 96 | знаков строки |
| `FMTLOG_LOKI_LABELS` | 4 | своих меток |

Реже нужны `FMTLOG_SNMP_PACKET_SIZE`, `FMTLOG_SNMP_OID_SIZE`,
`FMTLOG_LOKI_BODY_SIZE` и `FMTLOG_LOKI_TIMEOUT_MS` — они выводятся из
перечисленных и меняются вместе с ними; все они с пояснениями лежат в
[`src/LogConfig.h`](src/LogConfig.h).

Настройки форматирования — `FMTTINY_FLOAT_DECIMALS`, `FMTTINY_USE_DTOSTRF` —
описаны в [FmtTiny](https://github.com/240974a/FmtTiny#build-options).

## Сколько это стоит

Замерено сборкой, ESP8266. Журнал — прирост к пустой прошивке, приёмники —
к прошивке, где журнал и сеть уже есть:

| | флеш |
|---|---|
| журнал с выводом в порт | **+236 Б** |
| цветной вывод | +12 Б |
| уведомления по SNMP | +564 Б |
| telnet с историей и цветом | +2296 Б |
| строки для Loki | +2560 Б |
| журнал на веб-странице | +4268 Б |

Цвет почти ничего не стоит, пока вы не задаёте свои цвета: неиспользованные
таблицы линкер выбрасывает.

Сетевые приёмники различаются тем, что тянут за собой. SNMP шлёт UDP-пакет и
потому дёшев; Loki открывает HTTP-соединение; telnet и веб-страница поднимают
на плате сервер — он и составляет их цену. Сам WiFi в эти числа не входит: он
нужен приложению и так.

В RAM: буфер истории — 2048 байт у telnet, 4096 у веб-страницы; очередь
SNMP — 4 записи, пачка Loki — 16 строк.

Динамической памяти не выделяется нигде. Буфер сообщения один на приложение —
128 байт по умолчанию.

Подробные замеры форматирования — в [FmtTiny](https://github.com/240974a/FmtTiny).

## Платформы

| платформа | состояние |
|---|---|
| AVR (Uno, Nano, Mega) | проверено сборкой |
| AVR (ATtiny85) | проверено сборкой |
| ESP8266 | проверено сборкой |
| ESP32 | проверено сборкой |
| RP2040 (Pico) | проверено сборкой |
| STM32 (Blue Pill) | проверено сборкой |
| прочие | скорее всего работают, не проверялись |

`FmtTelnet.h`, `FmtWeb.h`, `FmtSnmp.h` и `FmtLoki.h` требуют сети и собираются
только на ESP — на остальных платах эти файлы пусты и сборке не мешают.

## Примеры

| пример | о чём |
|---|---|
| `Logging` | уровни, источники, свой приёмник вывода |
| `Color` | цветной вывод, свои цвета уровней и источников |
| `Telnet` | журнал по сети с историей для поздних клиентов |
| `Web` | журнал на веб-странице: цвет, поиск, выгрузка |
| `Snmp` | уведомления монитору: только то, что требует вмешательства |
| `Loki` | строки в Loki с метками, смотреть в Grafana |
| `Levels` | смена уровня на ходу и отсечение при сборке |

## Тесты

Можно запускать прямо на ПК:

```
pio test -e native
```

107 тестов: уровни и их перекрытие по источникам, приёмники, календарное
время, раскраска, история telnet с независимыми читателями, кодирование пакета
SNMP и тело запроса к Loki.

Пакет SNMP и JSON для Loki проверяются разбором: тест читает собранное и
сверяет поля, а не сравнивает байты вслепую.
